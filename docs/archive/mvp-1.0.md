## 1. 定位与取舍原则

### 1.1 目标用户

**手上有 Codex / Claude Code / agent 订阅的 crypto 用户。他们想挖头矿，来玩。**

他们的特征：

- 已经在为 agent 付费（$20–200/月），**有一笔沉没成本想变现**。
- 是雇佣兵，会互相拆台，也会互相刷。
- **不在乎 trustless，在乎能不能拿到。**
- 怕的是资金托管、拿不到、被 KYC —— 不是"不够去中心化"。

### 1.2 取舍原则（冲突时按此裁决）

```
① 速度 > 正确性          —— 叙事会被抄，先发优势决定成败
② 叙事 > 协议完整性      —— 不赚钱的协议不值得投入工程时间
③ 可验证 > 去中心化程度   —— 农民要的是"我的贡献被记录"，不是"数学上 trustless"
④ 10 分钟上手 > 任何架构优雅
⑤ 凡是 ARCHITECTURE.md 里的复杂机制 → 默认不做，除非它服务于 ①–④
```

### 1.3 核心洞察（整个 play 的基础）

**用户手上有一个被忽略的稀缺资源：agent 订阅的推理额度。**

| 性质 | 为什么重要 |
|---|---|
| **稀缺** | rate limit 是硬上限，不能无限刷 |
| **有真实成本** | 想放大产出 → 必须买更多订阅 → 这正是我们要的 |
| **可验证** | 推理产出有 hash，可锚定 |
| **自限** | 不需要复杂的反女巫规则 —— 他们被自己的账单限制了 |

**叙事：把你的 agent 订阅，变成一个能挖矿的资产。**

## 2. 已锁定的三项决策

| 决策 | 选择 | 含义 |
|---|---|---|
| **代币策略** | **积分先行** | MVP 不发币。积分是账本记录，不可转让。 |
| **工作量定义** | **agent 自生成任务 + 对抗验证** | agent 自己找活干；**只认可独立判定的任务类型**（§5.0）；随机验证者复核（§5.5）。 |
| **代币效用** | **待定** | 故意不定。纯叙事驱动，后面再补。 |

### 2.1 三项决策的直接后果（必须诚实面对）

- **积分先行 = 无价值锚。** 积分价格 = 对"未来 TGE"的纯预期。**兑现不了就归零。**
- **自生成任务 = 无真实需求方。** 工作量真实（消耗真金白银的额度），但**需求是自导自演的**。§5.5 的对抗验证与 §9.3 的真实需求前置条件是对此的回应。
- **效用待定 = 叙事最脆弱的一环。** 尽调第一个问题必然是"yield 从哪来"，必须有答案。

**这三条不解决，MVP 就是纯农场。** 见 §13 风险清单与 §15 待决问题。

## 4. 回执最小结构

回执是 MVP 的**唯一核心数据结构**。它必须做到：**任何人都能独立验证 agent 真的干了活，且不可伪造。**

```json
{
  "schema": "relayfirst.receipt.v1",
  "receiptId": "0x9a1c...",
  "agentId": "agent:eip155:8453:0x7F4d...A8B5",
  "epoch": 42,

  "task": {
    "type": "probe",              // probe | extract | compute（见 §5.0）
    "spec": { "url": "https://api.example.com/health" },
    "specHash": "sha256:3d4f...",
    "selfGenerated": true,
    "a2aTaskId": null             // 预留：未来接入 A2A 时放外部 task id（见 §16）
  },

  "work": {
    "provider": "openai|anthropic|local",
    "model": "gpt-5.5",
    "tokensIn": 1234,
    "tokensOut": 567,
    "startedAt": 1791015800,
    "finishedAt": 1791015862
  },

  "result": {
    "value": "200",               // 确定性结果（见 §5.0）
    "hash": "sha256:c1d9..."
  },

  "anchors": [
    {
      "url": "https://api.example.com/health",
      "contentHash": "sha256:7b2e...",
      "fetchedAt": 1791015810,
      "status": 200,
      "bytes": 20480
    }
  ],

  "verification": {
    "status": "pending",          // pending | verified | rejected
    "verifierId": "agent:eip155:8453:0xAb12...",   // 随机指派（见 §5.6）
    "verifiedAt": null,
    "stake": 50,                  // 验证者质押的积分（见 §5.6）
    "recomputedHash": null        // 验证者重算结果
  },

  "signature": "0x1b2c..."
}
```

### 4.1 四个关键字段

| 字段 | 作用 | 为什么不可省 |
|---|---|---|
| **`task.type` + `spec`** | 声明任务类型与参数 | **决定验证方式**；只有 `probe`/`extract`/`compute` 被接受（见 §5.0） |
| **`result.value`** | 确定性结果 | **验证者重算后比对的是这个值**，而不是模糊的"质量" |
| **`anchors[]`** | 外部可验证的锚定物 | **回执不能只是 agent 自称"我干了活"**。锚定物让任何人可重取验证。 |
| **`signature`** | EIP-712 签名 | 覆盖上述全部字段 —— 防篡改 |

### 4.2 签名覆盖范围

```
signature 覆盖 = keccak256(
    receiptId ‖ agentId ‖ epoch ‖ task ‖ work ‖ result ‖ anchors
)
```

**验证方不需要连任何服务器** —— 只需要回执本身 + 重取 anchors + 重算 result。这是"去中心"在这份 MVP 里唯一必须成立的技术点。

**注意：`verification` 不在签名覆盖内。** 它由验证者事后填写并单独签名，见 §5.6。

### 4.3 链上锚定（便宜版）

不逐条上链。**按 epoch 批量锚定**：

```solidity
// 每天一个 root，成本可忽略
mapping(uint256 epoch => bytes32 receiptsRoot) public epochRoot;
```

- 回执集 → Merkle tree → 每天提交一个 root 到 L2。
- 任何人可用 Merkle proof 证明"我的回执在 epoch N 里"。
- **不需要合约逻辑，只是一个 mapping。** 约 50 行 Solidity。

## 5. Proof of Agent Work：工作量与抗女巫

### 5.0 任务类型硬约束（最重要的一条）

**只接受有「独立 ground truth」的任务类型。** 这是整个抗女巫设计的地基 —— 因为**验证客观，就不需要争议仲裁层**。

| 任务类型 | 做什么 | ground truth | 谁都能验证 | 接受 |
|---|---|---|---|:--:|
| **`probe`** | 探测 URL 在 T 时刻的可达性 / 状态码 / 响应头 | 独立探测结果 | ✅ | ✅ |
| **`extract`** | 从页面抽取**指定字段**（如某 API 的某数值） | 重取可复现 | ✅ | ✅ |
| **`compute`** | 执行确定性计算（hash / 解析 / 格式转换） | 可复算 | ✅ | ✅ |
| ~~摘要 / 分类 / 翻译~~ | 生成类任务 | **无** | ❌ | ❌ |
| ~~fetch + 任意 hash~~ | 只证明"取过" | 无（见下） | ❌ | ❌ |

**为什么拒绝生成类任务：** 摘要"好不好"没有客观标准，**只能靠共识或主观仲裁** —— 那会立刻引入争议层、质押、裁决者，复杂度爆炸。**MVP 不做。**

**为什么拒绝"取任意 URL + hash"：** 它只证明 agent **访问过**某个 URL，不证明**取对了什么**。这是 v0 的最大漏洞（原 §5.5）。**已移除。**

> **这条约束的回报：验证是二值的（对/错），不是程度性的。** 因此 MVP **不需要** dispute / arbitration / slashing —— 见 §11。

### 5.1 工作量的定义

```text
1 份有效工作量 = 1 份满足以下条件的签名回执：
  ✅ 签名有效（EIP-712，EOA ecrecover）
  ✅ task.type ∈ {probe, extract, compute}          // §5.0
  ✅ 至少 1 个 anchor 可被重取验证（contentHash 匹配）
  ✅ result.value 可被验证者重算复现                 // §5.6
  ✅ 该 artifactKey 未被他人抢先提交                 // §5.2
```

### 5.2 抗女巫（一）：外部 artifact 全局去重

**`artifactKey` 是全局命名空间。**

```text
artifactKey = sha256(task.type + task.spec.url + contentHash)

账本（全局，非 per-agent）：
  artifactKey → firstSeenAt, firstAgentId, seenCount
```

**计分规则：**

| 情况 | novelty 系数 |
|---|---:|
| 该 `artifactKey` 首次出现 | **1.0** |
| 已被他人提交过 | **0.0**（不给分） |
| 同一 agent 重复提交同一 key | **0.0** |

**为什么有效：** 外部世界的**新内容**是有限的、不可伪造的。取同一个 URL 的第二个人**没有贡献新信息**，所以不给分。这一条让"开 1000 个 agent 刷同样内容"**收益为零**。

**为什么不会误伤：** `contentHash` 会随数据源更新而变化 → 新的 `artifactKey` → **取到新鲜内容的 agent 正常得分。**

### 5.3 计分公式

```text
points(receipt) = BASE × verified × novelty × diversity × budgetFactor

其中：
  BASE          = 10                      // 固定基数
  verified      = 1.0（验证者重算一致）
                = 0.0（不一致 → 拒收，且触发 §5.6 罚则）
  novelty       = 1.0 / 0.0               // 见 §5.2
  diversity     = 1.0 / (1 + sameDomainRepeats × 0.5)
                                          // 同一 domain 重复 → 递减
  budgetFactor  = 该 agent 本 epoch 已得分 / 全 epoch 上限
                                          // 防单点鲸鱼，见 §6.3
```

**`verified` 是 0/1 二值** —— 重算不一致的回执**直接作废**，不给部分分。这让伪造的期望收益为零。

### 5.4 验证窗口

```text
窗口 = 该 epoch 结束前（默认 24h）
epoch 结束后，只依赖已锚定的 root，不再重取
```

**注意：** 内容更新后重取会失败，所以回执**只在有限窗口内可验证**。这是可接受的取舍：**攻击者要伪造的是"提交时刻"的真实性**，窗口 > 0 就够了。

### 5.5 抗女巫（二）：对抗验证 + 质押

**自生成任务的弱点是"自己出题自己答"。修法是引入随机验证者。**

```text
1. A 自生成任务（probe/extract/compute）→ 产出 result
2. 协议随机指派验证者 B（B 不知道 A 是谁）
3. B 重取 anchor + 重算 result
4. B 质押积分下注：
     判「一致」→ B 得验证奖励；A 得 points
     判「不一致」→ 进入复核；错判方扣质押
```

**关键设计点：**

| 点 | 设计 | 理由 |
|---|---|---|
| 验证者随机指派 | 由协议分配，非自选 | 防止 A 指定同伙 |
| **质押用积分**（非代币） | `stake: 50` 积分 | **MVP 无代币**，质押只能是积分 |
| 验证者也要花额度 | B 必须真的重算 | 合谋成本 = 同时养 A 和 B |
| 二值判定 | 一致 / 不一致 | 有 ground truth，无需主观判断 |

**为什么"验证者也要花额度"是优点：** 合谋需要同时供养 A 和 B 两套 agent —— **这恰好是我们要的付费行为**，不是漏洞。

### 5.6 诚实声明：这不完美

> **大户养足够多 sybil，仍可自验（A 和 B 都是自己的）。**
>
> 成本随 sybil 数量**线性上升**，收益被 §5.2 的全局去重**压住**。这是**可接受的权衡，不是无懈可击。**
>
> **不要把它讲成无懈可击** —— 被拆穿一次，叙事就没了。

**MVP 的额外缓解：**

1. 验证者与被验证者的 `agentId` 必须不同。
2. 同一 `agentId` 不能在同一 epoch 内既大量产出又大量验证（比例上限）。
3. 验证奖励 < 产出奖励 → 纯验证不划算，必须有真实产出。

### 5.7 已知攻击面（更新版）

| 攻击 | 是否拦住 | 机制 |
|---|---|---|
| 开 N 个 agent 刷同样 URL | ✅ | §5.2 novelty = 0 |
| 伪造 anchor（编造 contentHash） | ✅ | 重取失败 |
| **取无价值内容刷分** | ✅ | **§5.0 任务类型约束** —— 只认可判定任务 |
| 生成类任务刷分 | ✅ | §5.0 直接拒收 |
| 买订阅刷量 | ❌ 不拦 | **这是付费行为，是我们要的** |
| 抢跑（监控后抢先提交） | ❌ 拦不住 | 抢跑者是第一个发现者，规则上合理 |
| **大户 sybil 自验** | ⚠️ 部分 | §5.6 —— 成本线性上升 |

## 6. 积分与 Emission 曲线

### 6.1 积分性质（诚实声明）

```text
积分（points）=
  - 账本内记录，不可转让
  - 无价格，不可交易
  - 唯一用途：未来 TGE 时的换算依据（若发生）
  - 不承诺任何回报
```

**必须写进 UI 和文档。** 这是法律与信任的底线。

### 6.2 全局 Emission 曲线

**不做固定发放，做"每 epoch 固定预算 + 按份额分配"。**

```text
epoch = 1 天

全 epoch 积分预算：  B(n) = B0 × decay^n
                     B0   = 1,000,000
                     decay = 0.99          // 每日衰减 1%

agent 在本 epoch 的得分：
  points_i = B(n) × (work_i / Σwork)
```

**这个设计的三个效果：**

| 效果 | 机制 |
|---|---|
| **头矿叙事成立** | 越早参与，同样的工作量分到越多（B(n) 递减，竞争者少） |
| **通胀可控** | 总预算指数衰减，不会无限膨胀 |
| **抗鲸鱼** | 见 §6.3 的 per-agent 上限 |

### 6.3 Per-agent 上限

```text
单个 agent 单 epoch 最多获得：  B(n) × 5%
```

**理由：** 防止一个大户用大量订阅额度独占产出，把散户挤走。**散户体验是这个 play 的命脉** —— 他们走了，叙事就没了。

### 6.4 为什么用积分而不是直接发币（在这个策略下）

| 维度 | 积分先行 | 直接发币 |
|---|---|---|
| 法律暴露 | 低 | **高** |
| 上线速度 | **快** | 慢（合约 + 审计 + 流动性） |
| 可调整性 | **可以随时改规则** | 规则上链后难改 |
| 农民信任 | 低（怕不给） | 高（即时可卖） |
| 退出成本 | **低**（不发币就无崩盘） | 高 |

**积分先行的最大好处：如果发现 play 不成立，你可以不发币，损失可控。** 这是给自己留的退路。

## 7. 节点规格（MVP 版）

### 7.1 最小节点（`relayfirst-node`）

```text
必须：
  1. 接受 HTTP（不是 WebSocket）—— 收件端点
  2. 按 agentId 存储消息（SQLite 单文件）
  3. 客户端拉取（GET）+ 可选 SSE 推送
  4. eventId / receiptId 去重
  5. 返回收件 acknowledgement
  6. 提供 /.well-known/relayfirst 信息文档

不做：
  ❌ EIP-712 验签（客户端自己验）
  ❌ 任何链读
  ❌ NATS / Redis / Postgres
  ❌ 多 edge / 负载均衡
```

**关键：节点是"哑"的。** 它只负责 store-and-forward，**不验证、不裁决**。验证由客户端做（§5.4）。

### 7.2 一键部署

```bash
docker run -d \
  --name relayfirst-node \
  -p 8080:8080 \
  -v ./relayfirst-data:/data \
  relayfirst/node:latest \
  --public-url https://relay.myagent.xyz \
  --storage sqlite
```

**验收：陌生人在 10 分钟内跑起来。** 见 §10。

### 7.3 为什么节点在 MVP 里这么薄

**因为节点不是护城河，是"去中心观感"的载体。** 用户要的是"我能自己跑"这个事实，不是节点的功能丰富度。

**参考 `ARCHITECTURE.md` §16** —— 那里有完整节点规格（RFN Core + 可选模块 + 8 种节点类型）。**MVP 只取最小子集，其余全部 Roadmap。**

## 8. 技术选型（定死）

**不争论，不在 MVP 期间更换。**

### 8.0 三分法（先看这个，别误读成"全自研"）

| 类别 | 策略 | 例子 |
|---|---|---|
| **① 密码学原语** | **永远用成熟库，绝不自研** | keccak256 · secp256k1 · `ecrecover` · X25519 · ChaCha20 |
| **② 编码 / 协议** | **优先用库**，除非有具体理由 | EIP-712 hashing · A2A 序列化 · HTTP · SQLite |
| **③ 业务数据结构** | **必须自研**（世界上没有） | RelayEnvelope · Delegation · Receipt · 计分 |

> **规则：密码学原语永远用库；业务数据结构永远自研；中间那层看情况。**
>
> **"自研"在本文只指第 ③ 类。** 第 ③ 类没有现成轮子，因为**它就是 RelayFirst 的产品本身**。

### 8.1 完整选型表

| 层 | 选择 | 类别 | 理由 |
|---|---|---|---|
| **Wire** | **`a2a-go`** | ② | 进外部社区生态；wire 自研零收益。见 §16 |
| **A2A 序列化** | **`a2a-go`** | ② | Agent Card 序列化 / Task 语义 |
| **keccak256** | **`golang.org/x/crypto/sha3`** | ① | 标准库级，**绝不自研** |
| **secp256k1 签名/验签** | **`github.com/decred/dcrd/dcrec/secp256k1/v4`** | ① | 纯 Go，**MIT 许可**，无 CGO |
| **`ecrecover`** | **`github.com/ethereum/go-ethereum/crypto`** | ① | 成熟；见 §8.2 的 LGPL 说明 |
| **EIP-712 hashing (Go)** | **`apitypes`** 或自研薄层 | ② | **二选一，都行** —— 见 §8.2 |
| **EIP-712 hashing (TS)** | **`viem`** | ② | **MIT**，业界标准，**不要自己写** |
| **HTTP 服务** | 标准库 `net/http` | ② | 零依赖 |
| **SQLite 驱动** | **`modernc.org/sqlite`** | ① | 纯 Go，**无 CGO** —— 关键，见 §8.3 |
| **CLI 框架** | **`github.com/spf13/cobra`** | ② | 生态标准 |
| **X25519 / ChaCha20**（后续） | **`golang.org/x/crypto`** | ① | 标准扩展库，**绝不自研** |
| **Merkle tree**（后续） | **`github.com/cbergoon/merkletree`** 或自研 | ② | 算法简单，但优先用库 |
| **Delegation** | **自研** | ③ | 差异化，无现成轮子 |
| **Receipt** | **自研** | ③ | 同上 |
| **Relay** | **自研，200 行级别** | ③ | 薄，可替换 |

### 8.2 关于 EIP-712：用库还是自研？（纠正）

**两条路都可行，选哪个不重要 —— 重要的是 §8.4 的 KAT。**

| 选项 | 优点 | 缺点 |
|---|---|---|
| **A. 直接用 `apitypes`** | 零代码；go-ethereum 维护 | 拖入 signer/core；LGPL-3.0 |
| **B. 自研薄 hasher（~200 行）** | 依赖干净；可读 | 要写代码 + 测 |

**关于 LGPL，说准确：**

- go-ethereum 是 **LGPL-3.0**。
- **LGPL 对"链接使用"通常可接受** —— go-ethereum 被大量商业产品使用。
- **它不是"不能用"，是一个"值得知道"的考虑。**
- 只有当你需要**静态链接 + 闭源分发**时才需要认真对待。

> **决策建议：**
> - **不想纠结 → 选 A**（用 `apitypes`），把时间花在 KAT 上。
> - **真的在意依赖干净 → 选 B**（自研薄层），因为 EIP-712 是**编码**、可测。

**EIP-712 是编码规范，不是密码学原语：**

```text
hashStruct(s) = keccak256(typeHash ‖ encodeData(s))
动态 bytes/string → keccak256(内容)
数组 → keccak256(拼接的 encodeData)
```

**规范完全确定，没有歧义。** 所以它可安全自研 —— 但**用库也完全正确**。

### 8.3 一个必须遵守的依赖约束：无 CGO

**整个节点必须能用 `CGO_ENABLED=0` 构建。**

理由：`docker run` 一条命令就能跑（§7.2）的前提是**静态单二进制**。CGO 会带来 glibc 依赖，破坏这一点。

| 需求 | 必须选 | 不能选 |
|---|---|---|
| SQLite | `modernc.org/sqlite`（纯 Go） | `mattn/go-sqlite3`（CGO） |
| secp256k1 | `decred/dcrd/dcrec/secp256k1`（纯 Go） | `btcec`（部分需 CGO） |

**CI 检查：`CGO_ENABLED=0 go build ./...` 必须通过。**

### 8.4 KAT 向量（真正的关键控制点）

**这是全文档最重要的工程要求，比"用不用库"重要得多。**

```text
testdata/eip712-vectors.json
  → 10 个用例，覆盖：
      嵌套 struct · 动态数组 · 长 string · 空值 · 多字节 UTF-8
  → 每个用例含：{ types, domain, message, expectedHash }
  → CI 中：
      TS（viem）算一遍 → 必须等于 expectedHash
      Go（你的实现）算一遍 → 必须等于 expectedHash
      不一致 → 构建失败
```

> **有这组向量，自研和用库的差别只剩 200 行代码。**
> **没有这组向量，用库也会在半年后炸** —— 因为跨语言边界 bug 无法靠"用库"避免。

**生成方式：** 用 viem 生成 `expectedHash` 作为基准（viem 是 MIT、业界标准），Go 侧对齐它。

### 8.5 关于 `a2a-go` 在 MVP 中的真实角色

**MVP 用它，但只用它的最小子集：**

```text
用：
  ✅ Agent Card 的序列化 / 校验（身份层）
  ✅ Task 生命周期语义（为未来 A2A 互操作留出形状）

不用：
  ❌ JSON-RPC over HTTP 的 server/client 实现（MVP 用自研薄节点）
  ❌ SSE streaming（MVP 用轮询，够用）
  ❌ push notification（需要公网 URL，农民大多没有）
  ❌ gRPC binding
```

**理由：** MVP 的 agent 是**自闭环挖矿**，没有外部 agent 参与。引入完整 A2A server 是**纯成本**。但用 `a2a-go` 的数据结构可以让未来的互操作**不必改回执格式**。

**关键约束：** `a2a-go` 只允许出现在**身份与序列化**边界，**不得**进入挖矿核心路径（§5）。挖矿核心只依赖自研回执。

### 8.6 为什么不把 A2A 放进 MVP 核心

见 §16。

## 9. CLI 上手体验（10 分钟）

### 9.1 目标路径

```bash
# 第 1 步：初始化（30 秒）
npx relayfirst@latest init
#   → 生成或导入 EVM 钱包
#   → 输出 agentId
#   → 提示：请配置推理额度来源（BYO API key）

# 第 2 步：配置（2 分钟）
npx relayfirst@latest config set --provider openai --api-key sk-...
#   或：--provider anthropic --api-key sk-ant-...
#   或：--provider local（本地模型）

# 第 3 步：启动挖矿（30 秒）
npx relayfirst@latest mine
#   → 守护进程开始
#   → 实时显示：本 epoch 积分 / 完成任务数 / 有效 anchor 数

# 第 4 步：查看贡献（随时）
npx relayfirst@latest status
npx relayfirst@latest receipts --export   # 导出全部回执，可离线验证
```

**首次产出积分应在 10 分钟内。** 这是 §11 的硬判据。

### 9.2 关键 UX 决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 入口 | `npx` | **零安装门槛** —— 这是 crypto 用户最熟悉的路径 |
| 钱包 | 生成或导入 | 不强制，降低门槛 |
| 额度来源 | **BYO API key** | 见 §9.3 风险 |
| 实时反馈 | 必须 | 农民要**立刻看到分数在涨**，否则不会留下 |
| 导出 | 必须 | "我能带走我的贡献"是信任的基础 |

### 9.3 头号技术风险：订阅不可编程驱动

**"消耗 Codex 订阅额度"这个叙事，可能无法用 API 实现。**

| 路径 | 可行性 | 经济含义 |
|---|---|---|
| **BYO API key**（按 token 付费） | ✅ **今天就能做** | 用户**额外**花钱，不是"变现沉没成本" |
| 驱动 Codex / Claude Code 订阅 | ❓ **未知** —— 需要核实是否开放程序化接口 | 若能做，叙事才真正成立 |
| 本地模型 | ✅ 可做 | 电费成本，无订阅叙事 |

**必须在上线前核实第二行。** 如果订阅无法程序化驱动，整个"把订阅变成矿机"的叙事**站不住**，退化为"再买一份 API 额度来挖矿"——吸引力大幅下降。

**MVP 策略：先做 BYO API key（保证能跑），同时并行核实订阅路径。**

## 10. 叙事与分发

### 10.1 核心叙事

```text
Grass      → proof of bandwidth
io.net     → proof of GPU
Helium     → proof of coverage
──────────────────────────────────
RelayFirst → proof of agent work      ← 新
```

**一句话：**

> **你的 agent 订阅，是一个可以挖矿的资产。证明你的 agent 真的干了活，就能拿到头矿。**

**为什么这个叙事在 2026 年成立：** 人人都在聊 agent，但**没人有办法证明"一个 agent 真的干了活"**。把这个缺口变成挖矿玩法。

### 10.2 "够去中心"对他们的真实含义

| 他们在意的 | 对应实现 | 状态 |
|---|---|---|
| 不托管我的资金 | **永不要求充值**，只连钱包 | 设计上成立 |
| 我的贡献被记录，且我能查 | 回执 + 链上锚定（§4.3） | 需实现 |
| 客户端开源，我知道它在干嘛 | 开源 CLI | 需承诺 |
| 能跑自己的节点 | `docker run` 单二进制（§7.2） | 需实现 |
| 能退出并带走 | 导出回执（§9.1） | 需实现 |
| 别 KYC | 无许可 | 设计上成立 |

**注意：六条里真正的"去中心化技术"只有第 2 和第 4 条。** 其余都是产品决策。**不要为这六条去做 1800 行的架构。**

### 10.3 真实需求：上线硬性前置条件

**这是最容易被跳过、但最致命的一条。已从"建议"升级为"硬性前置条件"。**

如果 yield 100% 来自通胀，尽调第一个问题就会击穿叙事：

> "yield 从哪来？" → "纯通胀" → **农民立刻折价离场**

**MVP 上线前必须具备（不可推迟到上线后）：**

```text
至少 1 个真实的付费/真实消费方
  → 让叙事从"纯农场"变成"有真实使用"
  → 不需要规模，需要【存在性证明】

推荐形态：让挖矿产出直接喂给网络的索引层
  → agent 挖出的数据真的被其他 agent 用于发现
  → "输出被消费"是事实，不是故事
```

**判据：** 如果有人问"你们的数据有人用吗？"，你能拿出**一个真实的消费者**，而不是"未来会有"。

**这不是工程任务，是运营任务，但它是上线的前置条件。** 见 §14 工期中的并行项。

## 11. 硬性验收判据

**MVP 算完成的定义（七条全过）：**

```text
① 陌生人 10 分钟内产出第一份积分
   → 从 npx 到看到分数，全程无人工协助

② 第三方离线验证回执
   → 关掉所有 RelayFirst 服务器，拿一份导出的回执，
     仍能独立验证 anchor + result + signature

③ 任意陌生人跑起自己的节点
   → 一条 docker 命令，不需要注册、不需要许可

④ 伪造工作量被拦住（红队测试）
   → 构造以下攻击，全部应得 0 分：
     a. 重复提交同一 artifactKey
     b. 编造 contentHash
     c. 开 5 个 agent 取同一 URL
     d. 提交生成类任务（非 probe/extract/compute）

⑤ 对抗验证闭环跑通
   → 随机指派验证者 → 重算 → 质押结算，全流程可跑
   → 且验证者判错时质押被正确扣除

⑥ 跨语言 KAT 通过（§8.4）
   → TS（viem）与 Go 对同一组向量产出【字节相同】的 hash
   → CI 中不一致即构建失败

⑦ CGO_ENABLED=0 构建通过（§8.3）
   → 单二进制可静态分发，docker run 不依赖 glibc
```

**② 和 ④ 是"这个 play 是不是真的"的判据。** ①③⑤ 是体验与机制判据，⑥⑦ 是工程底线。

**任何一条不过，不上线。**

## 16. 与 A2A 的关系

**这一节消除歧义。`MVP.md` 与 `ARCHITECTURE.md` 讲的是两个不同的故事。**

| | `ARCHITECTURE.md` | `MVP.md`（本文） |
|---|---|---|
| 故事 | "A2A 生态的厂商中立授权层" | "agent 订阅挖矿" |
| 时间尺度 | 长期 | **现在** |
| 用户 | 需要可验证授权/回执的企业与 agent | **想要 yield 的 crypto 用户** |
| 是否含 A2A | ✅ 核心（Wire = A2A 1.0） | ⚠️ **仅最小子集** |

### 16.1 MVP 是否包含 A2A？

**不含完整 A2A，只用它的最小子集。**

```text
用（§8.1）：
  ✅ a2a-go 的 Agent Card 序列化 / 校验
  ✅ Task 生命周期语义（为未来互操作留形状）

不用：
  ❌ A2A JSON-RPC server / client
  ❌ SSE streaming
  ❌ push notification
  ❌ gRPC binding
```

### 16.2 为什么 MVP 不需要完整 A2A

| 理由 | 说明 |
|---|---|
| **挖矿是闭环** | 用户的 agent 自己生成任务、自己产出回执 —— **全程没有第二个 agent** |
| **A2A 的价值是互操作** | MVP 里没有外部 agent，所以互操作价值 = 0 |
| **加它是纯成本** | A2A 的 Task/Message/Artifact **与"回执/积分"不对应**，映射是白做工 |
| **农民不看这个** | 农民要积分，不要互操作 |

### 16.3 什么条件下才引入完整 A2A

**当且仅当出现以下情况：**

```text
有真实的外部 agent（不属于你、不跑你的 CLI）需要与挖矿网络交互
  → 例如：外部需求方想发任务给农民
  → 例如：其他 A2A agent 想消费挖矿产出（对应 §10.3）
```

**在那之前，引入 A2A 只是给自己加依赖。**

### 16.4 预留：不把未来的路堵死

回执结构里预留了 **一个字段**：

```json
"task": {
  "a2aTaskId": null     // 未来接入 A2A 时放外部 task id
}
```

**一个字段的成本，换未来不必改回执格式。** 这是 MVP 为 A2A 做的**唯一**预留。
