# ADR-0004: 节点身份引入密码学，如何与「节点不能验签」共存

- 状态：**accepted**（2026-10-04 裁定：采纳选项 A —— 分二进制）
- 日期：2026-10-04
- 影响层级：**L0**（触及 `MVP.md` §7.1 的结构保证 + CI 门禁）
- 来源：外部评审清单 P0 第 1 条（S10-0）
- 依赖：S10-0（节点身份）

---

## ⚠️ 先读这一段

**本 ADR 是这份清单里最危险的一条。** 它可能被误读为"放宽节点约束"。
若下面的区分做不到，**就不该接入节点身份** —— 而不是先接入再补论证。

**必须成立的区分：**

| 节点获得的能力 | 是否允许 | 为什么 |
|---|---|---|
| 签**自己的结论**（"我认为回执 X 有效"） | ✅ **要的就是这个** | 判据 ⑩ 要求结论**可归因**；撒谎留下证据 |
| 验**他人回执的签名** | ⚠️ **需要论证** | 这是"节点能验签"，§7.1 明确禁止 |
| 伪**造回执**（签一份声称干了活的工作证明） | ❌ **绝不允许** | 这正是"节点不能伪造"要防的 |

**关键：第 1 行与第 3 行用的是同一把密钥。** 所以"节点有密钥"本身**不等于**"节点能伪造"——
伪造需要签**回执**（`RelayReceipt`），而结论签的是**断言**（`RelayVerifierAssertion`）。
**两个 EIP-712 struct 不同**（domain 也不同：回执 `1`/`2`，断言 `assertion-1`）。

**但这只解决了"技术上不能互用"，没有解决"结构上该不该给节点密钥"。** 见下方选项。

---

## 背景

判据 ⑩ 的原文：

> **⑩ 节点不可信但能干**
> → 节点能索引/查询/中转，且客户端在节点撒谎时仍能独立判定
> → **节点的验证结论可归因（节点签自己的结论）**

S10-5 已交付**机制**（`internal/assertion`）：能签、能验、客户端不盲信。
**但节点本身还没有密钥** —— 实测 `node.Config` 无密钥字段、`/.well-known/relayfirst` 不公布地址。

**接入节点身份会产生的冲突：**

```text
现有 CI 门禁（第 10 道）：
  relayfirst-node 的导入图【不得】含 eip712 / receipt / publish / store / scoring / mining
  理由：MVP.md §7.1「节点不能验签」→ 结构保证「节点不能伪造」

S10-0 要做的事：
  节点用 secp256k1 签自己的结论
  ⇒ internal/assertion 依赖 internal/eip712
  ⇒ relayfirst-node 必然链接 secp256k1
  ⇒ 门禁【必然】失败
```

**所以这不是"改个门禁"的小事，而是一个需要显式裁决的结构变更。**
默默放宽门禁 = 悄悄丢掉一条已被测试钉住的保证。

## 决定（**三个候选，待你裁定**）

### 选项 A：节点身份**可选**，且**分二进制**（推荐）

```text
relayfirst-node          ← 默认：无密钥，导入图不变，门禁不变
relayfirst-verifier      ← 新增：持密钥，出可归因结论

两者可同机运行，也可分开。
well-known 里 nodeId 字段【可选】：有则公布，无则明说"this node does not assert"。
```

| 优点 | 缺点 |
|---|---|
| 两条保证**同时**成立：无密钥节点仍不能伪造，有密钥节点结论可归因 | 多一个二进制 |
| CI 门禁**无需放宽**，只需**新增**一条针对 `relayfirst-verifier` 的门禁 | — |
| 一条 `docker run` 仍是无密钥最小节点（§7.2 承诺不破） | — |
| **与 ADR-0003 的"发行域"概念天然对齐**：验证者是域的成员，节点是传输 | — |

### 选项 B：节点身份**内置但可选**（同二进制，运行时决定）

```text
relayfirst-node --identity-key <file>   ← 给了就签结论；不给就只做传输
导入图【必然】含 eip712（因为二进制里有这段代码）
```

| 优点 | 缺点 |
|---|---|
| 一个二进制 | **导入图门禁必然失效** —— "节点不能验签"从**结构保证**降级为**运行时约定** |
| | 一个配置失误就能让节点持有密钥；而**结构性保证的价值正在于不依赖配置正确** |

### 选项 C：接入节点身份，**放弃**"节点不能验签"这条结构保证

| 优点 | 缺点 |
|---|---|
| 最简单 | **摧毁 MVP.md §7.1 的核心叙事**；"不可信但能干"里的"不可信"失去依据 |
| | 与 §7.3 的原始论证冲突（§7.3 纠正的是"不能干活"，**不是**"可以伪造"） |

---

## 建议

**选项 A。** 理由：它是唯一一个**同时**保住两条性质的方案 ——
而这两条性质（"节点不能伪造"与"结论可归因"）都是判据级的，不该二选一。

**并且它把冲突变成了分工**：节点 = 传输（不可信），验证者 = 结论（可归因、需质押）。
这与 `ARCHITECTURE.md` §5.7（relay vs authority 信任分离）是同一原则。

---

## 后果（若采纳 A）

1. **新增二进制 `relayfirst-verifier`**（或 `relayfirst node --assert` 的独立入口，但**独立编译单元**）。
2. **`relayfirst-node` 的导入图门禁不变** —— 这很重要，它证明"无密钥节点仍不能伪造"。
3. **新增一条门禁**：`relayfirst-verifier` 的导入图**不得**含 `internal/mining` 或任何能**签回执**的路径
   （即：它能签断言，不能签工作证明）。
4. `/.well-known/relayfirst` 新增**可选** `nodeId` + `asserts` 字段；**无密钥节点必须明说"不背书"**。
5. **判据 ⑩ 的验收测试**（见 TASKS.md §10.2c）在此之后才可跑。

**不可逆的部分：** 一旦节点身份公开（well-known 公布地址），撤回会让已缓存的 well-known 文档说谎。

## 证据

```text
MVP.md §7.1        —— 节点"不做 EIP-712 验签"，"不验证、不裁决"
MVP.md §7.3        —— "不可信但能干"；节点可验证但结论须可归因
MVP.md 判据 ⑩      —— "节点的验证结论可归因（节点签自己的结论）"
ARCHITECTURE.md §5.7 —— relay（不可信）vs authority（可验证）的信任分离
scripts/ci.sh      —— 第 10 道门禁：节点导入图不得含签名代码（实测有效）
internal/node/node.go Config —— 实测无密钥字段
internal/assertion —— 实测已具备签/验能力，但需调用方注入密钥
```

## 裁定结果

**✅ 采纳选项 A（分二进制）** —— 2026-10-04。

**已执行的后续动作：**

1. **`relayfirst-node` 导入图门禁不变** —— 它继续证明"无密钥节点不能伪造"。
2. **新增 `relayfirst-verifier` 二进制**，持密钥、出可归因结论。
3. **新增门禁**：`relayfirst-verifier` 的导入图**不得**含 `internal/mining`
   （即：**能签断言，不能签工作证明**）。
4. `/.well-known/relayfirst` 新增**可选** `nodeId`；**无密钥节点必须明说"不背书"**。
5. 判据 ⑩ 的验收测试（TASKS.md §10.2c）在此之后才跑。

**为什么这是唯一可接受的选择（记录理由，防日后被简化掉）：**

> 选项 B/C 都会让"节点不能伪造"从**结构保证**降级为**运行时约定**。
> 结构性保证的价值**正在于不依赖配置正确** —— 一个配置失误就能让节点持有密钥的系统，
> 与"节点在设计上不可能持有密钥"的系统，不是同一个安全等级。
