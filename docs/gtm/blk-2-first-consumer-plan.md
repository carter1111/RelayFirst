## 0. 先明确 BLK-2 是什么（一句话）

**我们能证明"某 agent 在 T 时刻看到了 X"，但还没有人为这个证明付过钱。**

`MVP.md` §10.3 的原话：

> 如果 yield 100% 来自通胀，尽调第一个问题就会击穿叙事：
> "yield 从哪来？" → "纯通胀" → **农民立刻折价离场**

**不需要规模，需要存在性证明** —— **一个**真实消费者就够。

---

## 1. 买家是谁（具体到角色）

**不要找"交易团队"，太泛。** 要找一个**具体到能叫出职位**的人：

| 优先级 | 角色 | 为什么可能痛 | 在哪找 |
|---|---|---|---|
| **①** | **中小量化团队的策略开发者** | 自己维护价格源，**单一 API 挂了就出事** | Twitter/X、GitHub、量化 Discord |
| **②** | **做套利 / MEV 的独立开发者** | 需要**多源交叉验证**的价格，防单点撒谎 | GitHub、Telegram 群 |
| **③** | **交易所/做市商的监控负责人** | 要证明"某 API 在 T 时刻真的活着" | LinkedIn、行业会议 |
| **④** | **研究/审计机构** | 要"某时刻确实观测到 X"的不可篡改记录 | 学术、合规圈 |

**我的建议：从 ① 开始。** 理由：

- **他们自己就在写代码** → 能直接看懂"可验证"的价值，不需要你解释
- **他们有明确的痛**（见下）
- **决策链短** —— 一个开发者觉得有用，就可能先用起来
- **不在监管敏感区** —— 比交易所容易谈

---

## 2. 他的痛点（不用我们也能描述）

**这一步很重要：痛点必须能独立成立。** 如果他的痛只有在我们出现后才存在，那不是真痛。

| 痛点 | 今天他怎么解决 | 为什么不够 |
|---|---|---|
| **单一价格 API 会挂 / 限流** | 接 2–3 个源，自己写 failover | 复杂度自己扛；且**不知道哪个源在撒谎** |
| **某个源返回了异常值** | 手工排查、加阈值告警 | 事后才知道；**无法证明是源的问题还是自己的 bug** |
| **监管/内部审计问"这个价格哪来的"** | 翻日志 | 日志**可被改**，不是证据 |
| **想验证某个数据源是否可信** | 长期观察、凭经验 | 没有**可量化的、第三方可复核**的记录 |

**共同点：他需要"可独立复核的观测记录"，而现在只能靠"自己相信自己的日志"。**

---

## 3. 我们给他看什么（一个 demo，不是架构）

**⚠️ 不要给他看 `ARCHITECTURE.md`、不要讲 A2A、不要讲积分。** 他只关心"能不能用"。

**Demo 应该只有一页输出：**

```text
$ relayfirst observations --subject api.example.com/ticker/BTCUSDT

subject:    api.example.com/ticker/BTCUSDT
predicate:  http_status
value:      200
window:     2026-10-04T10:00Z .. 10:05Z

evidence:
  agent 0x7d2e...  status 200  content sha256:9f3a...  ✓ verified
  agent 0x1b8c...  status 200  content sha256:9f3a...  ✓ verified
  agent 0x4a91...  status 200  content sha256:9f3a...  ✓ verified
                                          ↑ 3 个独立 agent 一致

→ 3 independent observers agree.
→ Each receipt is signed and re-verifiable offline:
    relayfirst verify receipt-0x7d2e.json
```

**这一页要说清三件事：**

1. **多源** —— 不是他自己接的 3 个源，是 **3 个独立 agent** 的观测
2. **可复核** —— 每份回执**离线可验**（关掉我们所有服务器也行）
3. **诚实** —— 一致就报一致；不一致就报不一致（**不要粉饰**）

**演示方式：** 现场跑一次，或录一段 60 秒的屏幕。**不要做 PPT。**

---

## 4. 他为什么会付钱（一句话）

> **"你现在得自己相信自己的日志；我们可以给你一份第三方可复核的观测记录，而且单个源挂掉不会让数据断。"**

**付费形态（建议顺序）：**

| 阶段 | 形态 | 说明 |
|---|---|---|
| **第一步** | **免费试用** | 让他先用，验证对他有用 —— **这一步不需要付钱** |
| 第二步 | 按查询量付费（USDC 或法币） | 他有真实用量后再谈 |
| 第三步 | 定制 predicate（他要的特定字段） | 这是他愿意多付的地方 |

**⚠️ 第一步是免费的，且这很重要。** BLK-2 要的是**存在性证明**，不是第一笔收入。
**"他持续在用"比"他付了 50 块"更有价值。**

## 5. 第一封联系信（可直接改）

**目标：不是卖，是问一个他愿意回答的问题。**

```text
标题：问一个关于你价格源 failover 的问题

你好，

我在做一个"可独立复核的观测记录"工具，想先确认它是不是真问题。

你的价格数据现在接几个源？当它们不一致时，
你怎么判断是源错了还是你的解析错了？

我在做的方向：多个独立 agent 各自观测同一个源，
每人签一份回执（可离线验证），然后交叉比对。
所以"这个价格哪来的"能变成一份可复核的证据，
而不只是你自己的日志。

如果你觉得这个方向有用，我可以跑一次给你看
（用你的一个公开源，5 分钟，不需要你装任何东西）。
如果你觉得没用，也告诉我 —— 我想知道为什么。

[你的名字]
```

**为什么这样写：**

- **不问"你要不要买"** —— 那会被直接忽略
- **问一个他专业上愿意回答的问题**（源不一致时怎么办）
- **明确给出退出方式**（"觉得没用也告诉我"）—— 这反而提高回复率
- **成本极低**（5 分钟，不用安装）

## 6. 怎么判断"他不感兴趣"（避免自我欺骗）

**这一步是为了防止你把"礼貌"当成"需求"。**

| 信号 | 含义 | 结论 |
|---|---|---|
| **"有意思，发我文档看看"** | 礼貌 | ❌ **不是兴趣** |
| **"我们现在用 X 就够了"** | 真不需要 | ❌ 换人 |
| **"你什么时候能上线？"** | 真兴趣 | ✅ 追 |
| **"能不能加一个 Y 字段？"** | **真兴趣**（在提需求） | ✅✅ **最强信号** |
| **"我拿你的数据和我的对一下"** | 真兴趣（在验证） | ✅ 追 |
| **他主动第二次找你** | **需求存在** | ✅✅✅ |

**判据（写下来，别靠感觉）：**

> **BLK-2 解决 = 有一个人，在我们还没上线时，就已经在用我们的输出做他的决定。**

**注意最后半句：** "用输出做决定" ≠ "觉得有意思"。前者才是需求。

## 8. 时间盒（防止无限期"还在接洽"）

| 阶段 | 时长 | 目标 | 失败则 |
|---|---|---|---|
| **A** | 第 1 周 | 联系 10 个候选人 | — |
| **B** | 第 2–3 周 | 拿到 2–3 次真对话 | 重写第 5 节的信（可能是措辞问题） |
| **C** | 第 4 周 | 至少 1 个愿意试用 | **回到 `MVP.md` 重新审视场景** |
| **D** | 第 5–8 周 | 他在真实使用 | 换场景（②③④）或重新考虑整个 play |

**⏰ 8 周后如果没有任何人使用：这是一个真实信号，不是"再等等"。**

`MVP.md` §10.3 把它列为**硬前置**，就是因为**它可能永远解决不了**。
那时正确的动作是**重新考虑场景**，而不是继续写代码。
