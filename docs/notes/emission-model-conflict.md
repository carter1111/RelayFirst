# 笔记：计分公式与 epoch 发行模型互相矛盾

- 发现日期：2026-10-04
- 严重度：**经济层定义冲突（需人裁决）**
- 状态：✅ **已裁决（2026-10-07）：模型 B —— 固定预算按份额**。理由与后续见 [`planning.md §A2`](planning.md)。
  **接线（`Allocate`/`CapAllocation`）尚未做**，且**要先改 `MVP.md`（L0）**。
- 相关：`MVP.md` §5.3、`MVP.md` §6.2、`MVP.md` §6.3、`internal/scoring/`

---

## 1. 现象

`MVP.md` 里有**两套互不相同的发行模型**，而且**只有一套在代码里生效**。

### 模型 A —— 按回执计费（`MVP.md` §5.3）

```text
points(receipt) = BASE × verified × novelty × diversity × budgetFactor
BASE = 10
```

每枚回执按公式**独立**计价。总量不是输入，而是**结果**：
有多少回执，就发多少分。

### 模型 B —— 固定预算按份额分配（`MVP.md` §6.2）

```text
points_i = B(n) × (work_i / Σwork)
B(n) = B0 × decay^n,  B0 = 1,000,000,  decay = 0.99
```

每个 epoch 有一个**固定预算**，按工作量份额分完。

### 二者不是同一个规则

| 维度 | 模型 A（§5.3） | 模型 B（§6.2） |
|---|---|---|
| 总量 | **输出**（随回执数增长） | **输入**（固定预算被分完） |
| 是否依赖他人工作量 | ❌ 完全不依赖 | ✅ 依赖 `Σwork` |
| 是否存在分母 | 无 | 有 |
| 竞争效应 | 无（别人多干不影响你） | 有（别人多干，你份额变小） |
| `BASE=10` / `B0=1e6` | 前者 | 后者 |

**最本质的区别：模型 B 有分母，模型 A 没有。** 这不是精度差异，是两种不同的经济。

---

## 2. 代码里实际生效的是哪一套

**模型 A。** 挖矿 → 计分走的是 `mining.ScoringSink` → `scoring.Emit` → `scoring.Score`，
即 §5.3 的公式。

**模型 B 的代码存在，但没有任何生产调用方。**

```bash
$ rg 'Allocate\(|CapAllocation\(' --glob '*.go' | grep -v _test.go
（无输出）
```

`Allocate` 与 `CapAllocation` 是**导出、有测试、有文档、也有详细注释**的函数，
但**除了本包自己的测试，无人调用**。

**所以：文档 §6.2 描述的东西，用户在真实挖矿里看不到。**

---

## 3. 量化差距

`internal/scoring/emission_conflict_test.go` 在同一组输入上跑两套模型
（10 个 agent × 10 枚回执 = 100 枚，epoch 0，所有系数取 1）：

```
模型 A（实现，§5.3）  :      1,000.00 分
模型 B（§6.2，比例 + 5% 上限）:   500,000.00 分（预算 1,000,000，单 agent 上限 50,000）
比值 A/B             :      0.0020    → 相差约 500 倍
```

并且模型 B 因为 **5% per-agent 上限**（§6.3）**没有把预算发完** ——
10 个等量 agent 各应得 10%，超过 5% 上限，于是 epoch 少发。
这在 `emission.go` 的注释里是**明文记录的刻意行为**，不是 bug。

第二个测试记录了结构性差异：**模型 A 的分数完全不受他人工作影响**
（他人做 100 倍工作，`agent:a` 仍是 10.00 分），而模型 B 必然被稀释。

## 4. 为什么这不是我能修的

**改发行是范围变化 + 经济决策。** 按 `AGENTS.md`：

> Agent 不决定"要不要做"，只决定"怎么做"。

具体地：

- 对齐到模型 B 会**改变每个矿工拿到的分数**，并引入"竞争稀释"这个新机制 ——
  那会改变头矿叙事（§6.2 声称"越早参与分越多"，模型 A 里并没有这个性质）。
- 对齐到模型 A 则是**删掉 §6.2/§6.3**，等于放弃固定预算与抗鲸鱼设计。
- 两者都会改变**已经写进文档的对用户的承诺**。

**所以必须先改 `MVP.md`（L0），再改代码。** 按 `AGENTS.md` §5.1，
范围变化必须先改 L0；只改 `TASKS.md` 或只改代码都算违规。

## 4b. ✅ 已裁决（2026-10-07）：模型 B，且 L0 已统一

**决定：模型 B（固定预算按份额）**，理由见 [`planning.md §A2`](planning.md)。
**`MVP.md` 已改**（先 doc diff 再动手）：

- **§5.3** 改为**只定义 `work`**（工作量），并写明 `points` 由 §6.2 在 epoch 末按份额结算。
- **§6.2** 加**结算步骤**（汇总 `Σwork` → 份额 → 5% cap → Merkle root）。
- **`docs/requirements.md`** 的 `REQ-SCORE-1/5` 同步。

**实现**：新增 `scoring.Settle(epoch, work)` = `CapAllocation(Allocate(work))` —— **一个函数**，
让调用方**无法只应用份额或只应用上限**。测试锁住 **decay** 与 **5% cap**。

**⚠️ 仍未接线**：`Emit` 仍按**每回执**写 points（模型 A 的形状）。**从"每回执写分"切到"epoch 末结算"
是账本模型变更**（S3 范围延伸），**未做** —— 见 `TASKS.md`。

## 5. 需要你回答的问题（已由 4b 取代）

**哪个是意图？**

1. **模型 A（按回执计费）** —— 那就把 `MVP.md` §6.2/§6.3 改成描述实际行为，
   或明确标注 §6.2 为 Roadmap。`Allocate`/`CapAllocation` 要么删除，要么标注为未接线。
   *后果：无固定总量，通胀不收敛；`budgetFactor` 是唯一的 epoch 约束。*

2. **模型 B（固定预算按份额）** —— 那就要实现"结算"：需要一个 epoch 结束后
   汇总 `Σwork` 并重算各 agent 份额的步骤，`Score`/`Emit` 的签名要能表达分母。
   *后果：分数在 epoch 结束前不可知；竞争会稀释收益，头矿叙事成立。*

3. **两者共存但分工不同** —— 例如按回执计"工作量点数"、按份额发"每日奖励"。
   那就需要明确写清两个数字各自是什么、给用户看哪个。

**我的建议：先确认 §6.2 是否仍是目标。** 因为 `decay=0.99^n` 加 per-agent 5% 上限
是"抗鲸鱼 + 头矿"叙事的技术基础，而当前实现**两个性质都没有**。
