# BLK-1 核实计划：订阅能否程序化驱动

日期：2026-10-04
状态：待执行（最高优先级，见 TASKS.md 第 1 节）
目标：一周内给出书面 yes/no 结论，记入 TASKS.md 第 1 节。在结论出来前，冻结 S10+ 的新投入。

## 1. BLK-1 是什么

RelayFirst Proof of Agent Work 的产品 thesis：用户的 agent 订阅（Codex / Claude Code，20-200 美元每月）是一笔沉没成本，挖矿让它变现，边际成本为零。

BLK-1 要回答：这些订阅能否被程序（而非手工在官方 UI/CLI 里操作）驱动去执行挖矿任务？

- YES：闭环成立，用户把现有订阅指过来就行。
- NO：叙事退化成再买一份 API 额度来挖矿，经济账算不过来，冷启动引擎死。

这是整个产品的生死项（MVP 第 9.3 节风险 R1，极高严重度），不是技术细节。

## 2. 核实方法：三个问题乘以每个目标订阅

目标订阅（按 MVP 第 1.1 节目标用户持有情况，优先测前两名）：

1. Claude Code（Anthropic 订阅）
2. Codex（OpenAI 订阅）
3. 其他（按用户调研补充）

每个订阅回答三个问题：

(a) 技术路径存在吗？
- 是否有非交互模式（CLI 的非交互 flag、官方 API、headless 运行）？
- 能否无人值守跑完一个完整任务（以 probe 任务为探针）？
- 鉴权方式是什么（订阅凭证能否用于程序调用）？

(b) ToS 允许吗？
- 服务条款是否区分订阅（交互使用）与 API（程序化使用）？
- 程序化驱动订阅是否会导致封号？找条款原文，截图存证。
- 注意：技术上能跑但 ToS 禁止等于 NO。这条比技术更重要。

(c) 无人值守可靠吗？
- 长时间运行稳定性（掉线重连、限流行为）。
- 输出是否机器可解析（挖矿需要结构化产出，不是人类聊天）。

## 3. 判定标准

- 每个订阅给书面 yes/no，附证据（命令、截图、条款链接）。
- 结论记入 TASKS.md 第 1 节，格式：BLK-1 加 YES/NO/PARTIAL 加一句话加证据链接。
- 若全 NO：主路径切为 BYO API key（已规划的缓解方案），并重新评估挖矿叙事是否成立。这是一个产品级决策，需要用户拍板，不是工程能解的。
- 若 PARTIAL（部分订阅行）：支持列表只写 yes 的，文档明确标注。
