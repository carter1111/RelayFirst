## 0. 一句话结论

**S13 的正确形态不是"给消息加密"，而是"把密钥权威分层"。**

加密只是其中一层。真正的设计约束来自一个问题：**"节点可以代签吗？"**
答案是可以 —— **但只能代签会话级事件，且主密钥永不出用户边界**。
这条同时解决了 MCP 的密钥问题（提案 §9）。

## 2. 密钥层级：四层，三层分离

**提案 §8.3 的设计，逐层说明"为什么必须在那一层"：**

```text
① Owner / Smart Account          ← 资产权威（硬件钱包 / Passkey）
        │  EIP-712 签名（一次，链下）
        ▼
② Session Delegation             ← 作用域 + 额度 + 有效期 + nonce
        │  派生
        ▼
③ Session Signing Key            ← 热路径签名；只能【行使】被委托的权限
        │  独立生成（与②无关）
        ▼
④ X25519 Encryption Key          ← 只加密；对资产【零权威】
```

### 2.1 三条"必须分离"，以及每条防的是什么

| 分离 | 防止的攻击 | 为什么不能合并 |
|---|---|---|
| **① ≠ ③**：Owner 与 Session Key | Session Key 泄露 → 资产被提取 | Session Key **只能行使、不能扩大**权限；且 Owner 递增 nonce 即可**整体撤销** |
| **② ≠ ④**：Delegation 与 Encryption Key | 加密密钥泄露 → 签名能力泄露 | **Encryption Key 独立生成**，泄露**无法签名、无法动资产** |
| **③ ≠ ④**：签名与加密密钥 | 一把密钥两用 → 一处泄露全丢 | **签名密钥与加密密钥无关**；`ARCHITECTURE.md` §6.1 要求二者独立 |

> **核心不变量：**
> **加密密钥的泄露，不得导致任何签名能力或资产移动能力。**

### 2.2 为什么 Encryption Key 必须独立生成，而不是"从签名密钥派生"

**这是一个容易做错且后果严重的选择。**

从签名密钥派生（哪怕用 HKDF）看起来更省事，但它意味着：

```
签名密钥泄露 → 加密密钥可被派生 → 历史密文全部可解
```

**独立生成则**：签名密钥泄露**不影响**加密密钥，历史密文仍安全。
代价是多一份密钥要保管 —— **这个代价必须付。**

**⚠️ 注意与 §6.3 的张力**：`X25519` 需要**长期公钥可被发现**（否则别人无法给你加密）。
所以 Encryption Key 需要一个**发布机制**，见 §6.3。

## 3. 协议层：加密载荷放在哪（**这是本方案最需要你确认的一点**）

### 3.1 问题

`MVP.md` §17.4（A9 §④）要求**签名载荷逐字签名**：
验证者对**收到的字节**做哈希，**绝不重新序列化**。

**加密与这条的关系是什么？** 有两种做法，后果完全不同：

| 选项 | 做法 | A9 影响 | 评价 |
|---|---|---|---|
| **A. 加密 `payload` 之后仍逐字签名** | 密文进 `payload` 字节，签名覆盖**密文**。验证者哈希字节，**不解密也能验签** | ✅ **零影响** | ✅ **推荐** |
| B. 加密整个回执 | 信封里放 `encryptedReceipt`，签名在密文内 | ⚠️ 验证者**无法在不解密的情况下验证签名** | ❌ 破坏判据 ② |

**选 A，理由：**

> **判据 ② 要求"关掉所有服务器仍能验签"。** 若签名在密文内，验证就需要**解密**，
> 而解密需要密钥 —— 那么一份**交给第三方的回执**就无法被第三方验证。
> **A 保留了"任何人都能验签"，只是只有持有者能读懂内容。**

### 3.2 具体形状

```text
回执（未加密，任何人可验签）
  payload:     {"encrypted": true, "alg": "XChaCha20-Poly1305", "epk": "...", "nonce": "...", "ct": "..."}
  signature:   覆盖上述字节（密文是字节，不是结构）
```

**关键：** `payload` 是**不透明字符串**，签名覆盖的是**它的字节**。
这与 S9-0b2 的"逐字 blob"是**同一个模式** —— 加密载荷只是 blob 的一种内容。

**⚠️ 这意味着：**

- **验证者不需要密钥** → 判据 ② 完好
- **节点不需要密钥** → §7.1 完好
- **只有持有者能读懂** → 隐私成立

### 3.3 需要标注的字段（**不得**在签名之外）

`encrypted` / `alg` / `epk`（临时公钥）/ `nonce` 都**必须在签名覆盖的字节内**。
若放在签名之外，中间人可以**改 `alg`**（降级攻击）或**换 `epk`**（重定向解密）。

> **规则：任何影响"谁能读懂"的字段，都必须被签名覆盖。**

## 4. Session Delegation 最小版

### 4.1 委托包含什么

按提案 §8.3 与 `TASKS.md` S13-3 的"作用域 + nonce 撤销"：

```text
SessionDelegation {
  owner:        agentId（资产权威）
  sessionKey:   Session Signing Key 的公钥/地址
  scope:        允许做哪些事（如：只能签 SESSION_*/TASK_PROGRESS 事件，不能签 RECEIPT）
  budget:       额度上限（数量 + 单位）
  validFrom / validUntil
  nonce:        单调递增；Owner 递增即整体撤销
  signature:    Owner 的 EIP-712 签名
}
```

### 4.2 三条硬规则

| 规则 | 说明 |
|---|---|
| **不能扩大** | Session Key **只能行使**被委托的权限。扩大 = 需要 Owner 重签 |
| **单调 nonce 撤销** | Owner 递增 nonce → 该 delegation 立即失效。**无需上链**（用最新 nonce 即可判定） |
| **不签回执** | **回执必须 Owner 亲签**（或经 S13-3 的受限签名）。见下 |

### 4.3 ⚠️ 最危险的一条：Session Key 不得签回执

**理由：** 回执是**积分与赏金的唯一凭证**。若 Session Key 能签回执，
则**一次会话密钥泄露 = 可以无限刷积分**。

> **规则：`scope` 必须显式排除 `RECEIPT`。**
> 这条要有**测试**，不能只写在文档里 —— 参考 `RelayPoints` 的 soulbound 检查：
> **声明不够，必须有强制机制 + 一个会失败的测试。**

### 4.4 与 §7.1 的一致性

节点**可以代签会话级事件**（省去用户每笔都签），但它代签的是**它自己权限内的东西**；
**节点仍不能验签、不能解密、不能签回执**。三者一致。

## 5. MCP 的密钥问题（S13-4）

**提案明确：MCP server 绝不能持有主密钥。**

| 操作 | 谁做 | 密钥位置 |
|---|---|---|
| **发现 / 认领 / 提交** | MCP | ❌ 无需密钥（只转发） |
| **签回执** | **本地 CLI** | ✅ 用户边界内 |
| **签会话事件** | MCP（经 delegation） | ✅ 只有受限会话密钥 |
| **解密私有 payload** | 用户客户端 | ✅ 加密密钥在用户侧 |

**核心：** MCP **只转发已签字节**。若它能签名，`prompt injection` 就能让 agent **替用户签任意回执**。

> **这条是 MCP 设计的**唯一**关键约束**，其余都是普通 HTTP 客户端。

## 6. 三个需要你拍板的设计点

### 6.1 加密密钥的发布方式

X25519 公钥必须可被发现（否则别人无法给你加密）。选项：

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. Agent Card extension** | 卡片加 `encryptionKey` 扩展（与 relay set 同一模式） | ✅ 复用 A9-safe 扩展机制；✅ 签名覆盖 → 不可伪造 | 需要卡片的**时效性**保证（卡片可更新） |
| B. 链上登记 | 地址 → 公钥 mapping | ✅ 权威、可发现 | 需要 gas；且**轮换密钥要上链** |
| C. 带外交换 | 双方直接交换 | ✅ 无基础设施 | ❌ 无法给陌生人加密 |

**建议 A**（与 P1 #3 的 relay-set 完全同一模式：extension，`Required: false`，签名覆盖）。
**⚠️ 但有一个诚实弱点**：卡片可更新 → **读到的可能是旧公钥**。
故**密文里必须带 `epk`（临时公钥）**，接收方用**私钥**解，**不依赖卡片时效**（见 §3.3）。

### 6.2 是否引入"加密回执"变体，还是复用 v1 结构

- **建议复用**：`payload` 变成"加密 blob"，**结构不变**（§3.2）。
- **好处**：v1 回执**完全不变**（A9 零影响），验证者代码**无需改动**。

### 6.3 `alg` 字段的协商

**不要在签名内放"版本常量并要求精确匹配"**（A9 §②禁止）。
建议：`alg` 是**字符串**，验证者**不认识就跳过解密**（但仍能验签）——
这与"未知 schema major 仍可验签"是**同一模式**。

## 8. 建议的开工顺序（与理由）

```text
① S13-1  →  ② S13-2  →  ③ S13-2b  →  ④ S13-6  →  ⑤ S13-5（部分）
                                    ↓
                              ⑥ S13-3  →  ⑦ S13-4
```

**为什么 S13-2b 必须紧跟 S13-2**：加密本身是库调用，**不难**；
难的是**"哪些字段必须被签名覆盖"**。若先做 3/4 再补 2b，
**降级攻击的窗口会一直开着**，且补的时候要动已上线的结构。

**为什么 S13-3 排在后面**：它是**权限系统**，最危险（§4.3），
且它的正确性依赖 **S13-2b 已确立"什么必须被签名"**。
