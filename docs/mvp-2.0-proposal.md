## 0. 这次变更要解决什么

MVP 1.0 做了一台**验证机**：签名回执、离线可验证、全局去重、积分记账。机制扎实。

但它有一个**定位漂移**：仓库里躺着两份互相矛盾的产品定义。

| | `ARCHITECTURE.md` | `MVP.md` |
|---|---|---|
| 定位 | 去中心化 **headless A2A 协调织物** | **agent 订阅挖矿** |
| 核心价值原话 | *"核心价值**不是**支付、挖矿或区块链"* | *"把你的 agent 订阅，变成一个能挖矿的资产"* |
| 矿工 | §1.5 **"不做矿工"** | 整个 MVP 就是矿工 |

**用户裁决（2026-10-04）：**

> **对外定位 = 去中心化 headless A2A 协议。这个本质不能变。**
> **挖矿是引流机制。但 MVP 也必须有一个合理、可用、正常的 A2A 协议及节点。**

所以 2.0 不是"挖矿加功能"，也不是"A2A 取代挖矿"，而是：

```text
本体   = A2A 协议 + 节点        ← 对外形象，必须完整可用
引流   = 挖矿机制               ← 拉用户进来的玩法，必须真实
两者关系 = 挖矿跑在 A2A 协议之上，而不是两套东西
```

**1.0 的错误不是"做了挖矿"，而是"把挖矿当成了产品本身，A2A 只剩一个 4 字段信封"。**

## 1. 范围（2.0 做什么）

### 1.1 三个层次

```text
L1  A2A 协议层（本体）
    Agent Card · Session · Task · Message/Event · Receipt
    ↑ 用官方 A2A SDK 做 wire；RelayFirst 只自研 authority/回执/结算

L2  节点层（本体）
    索引 · 查询 · 任务中转 · 可验证但不被信任
    ↑ 从"哑节点"升级为"不可信但能干"

L3  挖矿层（引流）
    保留 1.0 全部机制（回执/去重/积分），但改成"一种任务来源"
    ↑ 挖矿 = 无需求时的默认供给；A2A 任务 = 有需求时的定向供给
```

### 1.2 明确继承 1.0 的部分（不动）

| 资产 | 为什么保留 |
|---|---|
| 回执结构 + canonical JSON | A2A 的 `Receipt` 就是它，已验证 |
| EIP-712 签名 + 跨语言 KAT | 不变式 A4，仍门禁 |
| 全局去重账本 | 挖矿层的承重机制，不变式 A6 |
| 二值验证（重跑 + anchor 重取） | **任务验证的一种模式**，见 §2.2 |
| 静态二进制 + no-CGO | 不变式 A3，节点分发的前提 |
| 积分账本（不可转让） | 见 §3，形态待定 |

### 1.3 本提案要推翻或修改的

| # | 原约束 | 2.0 改成 | 影响 |
|---|---|---|---|
| **A2** | 任务类型只准 `probe`/`extract`/`compute` | **任务自己声明验证模式**（`recompute` / `evaluator` / `dispute`） | §2.2 |
| **§7.3** | 节点必须"哑" | 节点**不可信但能干**（索引/查询/中转/可归因验证） | §4 |
| **A5** | 积分不可转让、不定价、不承诺回报 | **待定**：见 §3 的形态选择 | §3 |
| **A7** | 不做 token 挖矿/质押奖励 | **待定**：取决于 §3 | §3 |

> **A1（不手写密码学）、A3（no-CGO）、A4（KAT）、A6（全局去重）、A8（不碰 sibling）继续全部有效。**

## 2. A2A 协议层（本体）

### 2.1 一等对象 —— 现在缺什么

`ARCHITECTURE.md` §4.1 定义了 8 个一等对象。**MVP 1.0 只有 1 个（Receipt，且被挖矿专用）。**

| 对象 | 说明 | 1.0 有? | 2.0 |
|---|---|---|---|
| **Agent Card** | 能力、端点、签名身份 | ❌ | ✅ **必须** |
| **Session** | 多 agent 协调上下文 | ❌ | ✅ **必须** |
| **Task** | 有状态机的长任务 | ❌ | ✅ **必须** |
| **Message / Event** | 见 §2.3 | ❌ | ✅ **必须** |
| **RelayEnvelope** | 签名信封 | 🔸 只有 4 字段的 `Envelope` | ✅ 扩展 |
| **Receipt** | 执行回执 | ✅ 完整 | ✅ 复用 |
| **Delegation** | 会话委托授权 | ❌ | 🔸 2.1 |
| **Approval** | HITL 审批 | ❌ | 🔸 2.1 |

### 2.2 任务类型不再受限 —— 靠"验证模式"字段

**这是解开 1.0 最紧那条约束的关键。** A2 约束的是**验证路径**，不是**任务来源**。这两件事正交：

| 谁定目标 | 任务内容 | 能否二值验证 | 需要争议层 |
|---|---|---|---|
| 自己 | `probe`/`extract`/`compute` | ✅ | ❌ |
| **别人（A2A）** | `probe`/`extract`/`compute` | ✅ **仍然可以** | ❌ |
| 别人（A2A） | 摘要/翻译/写代码 | ❌ | ✅ **必须** |

**做法：任务自己声明验证模式。**

```json
{
  "task": {
    "type": "extract",
    "verification": "recompute",
    "spec": { "url": "...", "field": "..." },
    "bounty": { "amount": "50", "asset": "points" }
  }
}
```

| `verification` | 怎么验 | 谁验 | 2.0 做? |
|---|---|---|---|
| `recompute` | 重跑任务 + 重取 anchor | 任何节点/客户端 | ✅ **复用 1.0 验证器** |
| `evaluator` | 指定评估者给分 | 另一个 agent 或模型 | ✅ 做机制，策略后置 |
| `dispute` | 仲裁 | 人或治理 | ❌ **2.1**（先把低成本路径跑通） |

**好处：** 任务市场不需要让每个任务都背争议层。便宜的自动验任务走快路，贵的主观任务走慢路并付更高成本。

### 2.3 Message / Event 层 —— 你说的"沟通层"

**确认存在且必须做。** `ARCHITECTURE.md` §4.4 有 29 个事件类型，分四类：

| 类别 | 例子 | 作用 |
|---|---|---|
| **会话** | `SESSION_OPEN` / `SESSION_CLOSE` | 建立/结束协调上下文 |
| **身份** | `AGENT_CARD_PUBLISH` / `_UPDATE` | 发布/更新能力 |
| **任务** | `TASK_CREATED` → `_OFFERED` → `_ACCEPTED` → `_STARTED` → `_COMPLETED` | 任务全生命周期 |
| **交互** | `TASK_PROGRESS` / `TASK_WAITING_FOR_INPUT` / `TASK_INPUT_PROVIDED` | **双向沟通** |
| **回执/结算** | `RECEIPT_ISSUED` / `SETTLEMENT_CLAIM` | 产出与结算 |

**每个事件都是一条签名消息。** 所以"message 层"= 事件表 + Session 上下文。

**Ephemeral 信号（presence/typing/heartbeat）不进签名信封** —— 它们是传输层信号，不是协议对象。

### 2.4 Task 状态机

`ARCHITECTURE.md` §4.5 定义了完整状态机，**每个非终态都有超时边**（v1 修正 #5 补的）。

**2.0 建议：实现完整状态机的节点，但超时边先做 4 条**（`OFFER_TTL` / `ACCEPT_START_TTL` / `INPUT_TTL` / `APPROVAL_TTL`），其余后置。理由：没有超时边的任务会**永久挂起**，这是真 bug；但 6 条全做是过度工程。

### 2.5 Wire 层用官方 A2A SDK

**`ARCHITECTURE.md` §1.2 原话：**

> **Wire = A2A 1.0。Authority + Receipts + Settlement = RelayFirst。**

所以：

- **不自研** Agent Card / Message / Task 的线格式 → 用 A2A SDK
- **自研** RelayFirst 独有部分：`RelayEnvelope` / `Receipt` / `Settlement` / 去重

**理由：** 不重造轮子，且 A2A 生态的客户端能直接对接。

## 3. 积分形态 —— 必须选一种，不混合

**用户裁决：** *"不要越搞越复杂，要么做 token（积分币），要么做 SBT，要么做一个直观的 NFT（有积分），不是什么都混合。"*

### 3.1 三个候选（互斥）

| 方案 | 是什么 | 钱包里长什么样 | 可交易 | A5/A7 |
|---|---|---|---|---|
| **① 积分（现状）** | 链下账本记录 | 看不到（要 CLI） | ❌ | ✅ 保住 |
| **② SBT / NFT** | ERC-721 + ERC-5192 + override | 一个徽章 NFT，点进去看 attributes | ❌ | ✅ 保住 |
| **③ Token** | ERC-20 | 主列表显示余额 | ✅ | ❌ **推翻** |

### 3.2 如果选 ②（SBT/NFT），关键技术细节

**必须纠正一个常见误解：**

> **`ERC-5192` 只是加一个 `locked()` 声明，它本身不阻止转让。**

完整实现需要**两件事**：

```solidity
// 1. ERC-5192 声明
function locked(uint256 tokenId) external view returns (bool) { return true; }

// 2. 真正的拦截（关键，只做第 1 步是不够的）
function _update(address to, uint256 id, address auth) internal override returns (address) {
    require(to == address(0) || _ownerOf(id) == address(0), "soulbound: non-transferable");
    return super._update(to, id, auth);
}
```

**积分怎么放（三种，各有取舍）：**

| 做法 | 直观度 | 问题 |
|---|---|---|
| NFT 存余额，`attributes.points` | 🔸 要**点进去**看 | 最省 gas ✅ 推荐 |
| 每笔积分一个 NFT | ❌ 钱包里一堆垃圾 | gas 灾难 |
| ERC-20 禁用 transfer | ✅ 主列表直接显示数字 | **看起来像币**，与"不是平台币"定位冲突 |

**建议：徽章 NFT（承载身份+声誉）+ `tokenURI()` 动态返回积分 + 一个网页看余额。**
不要为了"钱包一眼看到"选 ERC-20 —— 那会毁掉定位。

### 3.3 关于"积分没有 inflation"与"后期空投平台币"

**用户的论证：** *"如果是积分，就不是价格的东西，不存在 inflation。积分在后期可以空投平台币（到平台币 launch 时），不存在矛盾。"*

**这个论证基本成立，但有一处必须显式处理：**

`MVP.md` §6.1 已经把"未来 TGE 换算依据（**若发生**）"写进积分用途，所以**文档本身不排斥**这件事。

**但 `HANDOFF.md` §5.3 有一句必须面对：**

> *"这个退路只在你不提前承诺空投时才存在。"*

区别在于措辞：

| 说法 | 性质 | 合规 |
|---|---|---|
| "积分**可能**在未来的 TGE 中作为换算依据（若发生）" | 条件式、无承诺 | ✅ |
| "积分**将**空投平台币" | **承诺** | ❌ 摧毁"不发币"退路 |

**具体影响：A5 合规守卫（`internal/compliance`）会把 `airdrop` 判为风险词。**
若 2.0 要在文档里谈这件事，**必须用条件式措辞**，或把它加入批准免责语白名单 —— 后者是一次需要留痕的决策，不能悄悄做。

## 4. 节点层（本体）—— 从"哑"到"不可信但能干"

### 4.1 现状

端点只有四个：

```
POST /messages            收件
GET  /messages/{agentId}  拉取
GET  /healthz
GET  /.well-known/relayfirst
```

打包是好的：`docker run` 一条命令，36.5MB 静态二进制，非 root，带 healthcheck。

**功能是薄的。** 没有索引、没有查询、没有任务中转。

### 4.2 关键纠正：「哑」被用错了

**`MVP.md` §7.3 的真实意图是"节点不可信"，不是"节点不能干活"。** "哑"是偷懒的近似。

正确的约束应该是：**客户端的验证结论不依赖节点。**

| 节点能做的事 | 破坏安全吗 | 结论 |
|---|---|---|
| 索引 / 查询观测 | ✅ 不会（数据可重验） | **加** |
| 聚合 / 排序 / 交叉验证 | ✅ 不会（客户端可复算） | **加** |
| 任务中转（market relay） | ✅ 不会 | **加** |
| **自己验签并给"通过"结论** | ⚠️ **仅当客户端盲信时** | **加，但结论可归因** |

### 4.3 「不可信但能干」的实现

```text
节点可以验证，但必须把自己也签一份：
  节点给结论 = 签一份 "我认为回执 X 有效" 的回执
  → 撒谎就留下证据 → 可被 slashing
  → 客户端仍独立复验，节点只是加速器
```

这与 `ARCHITECTURE.md` §5.7（relay vs authority 信任分离）是同一原则的轻量版。

### 4.4 节点要新增的能力

| 能力 | 端点（建议） | 作用 |
|---|---|---|
| Agent Card 发布/发现 | `POST/GET /agents` | 让 agent 被找到 |
| 任务发布/认领 | `POST /tasks` · `GET /tasks` · `POST /tasks/{id}/claim` | 任务市场 |
| 观测索引 | `GET /observations?subject=...` | **让产出可被消费** |
| 交叉验证视图 | `GET /observations/{id}/evidence` | 多 agent 独立验证 |
| 事件流 | `GET /events`（SSE，可选） | 实时协作 |

**`ARCHITECTURE.md` §5.3 的 Indexer / Projection 就是要抽的东西。**

## 5. 挖矿层（引流）—— 改成"一种任务来源"

### 5.1 重新定位

```text
挖矿 = 无需求时的默认供给
       agent 从配置的 URL 自生成 probe/extract/compute 任务
       verification = "recompute"（复用 1.0 验证器）

A2A 任务 = 有需求时的定向供给
       别人发布任务 + 赏金 → agent 认领 → 执行 → 提交
       verification 由任务声明
```

**两者共用同一套回执、验证、去重。** 挖矿不是"另一套系统"，是任务来源的一种。

### 5.2 保留的全部 1.0 机制

- 全局去重（`artifactKey = sha256(type + url + contentHash)`）—— 不变式 A6
- 二值验证（重跑 + `AnchorConsistency` 重取）
- 积分记账 + `budgetFactor` / `diversity`
- 对抗验证 + 承诺账本

### 5.3 yield 的来源（必须说清）

`MVP.md` §10.3 原话：

> 如果 yield 100% 来自通胀，尽调第一个问题就会击穿叙事：
> **"yield 从哪来？" → "纯通胀" → 农民立刻折价离场**

| yield 类型 | 谁付 | 可持续 |
|---|---|---|
| **通胀 yield** | 协议凭空印（emission） | ❌ |
| **需求 yield** | **买家付的赏金** | ✅ |

**1.0 只有第一种。这就是 BLK-2。**

**关键：A2A 节点本身不产生 yield，也不产生买家。**

```text
A2A 节点 = 水管（让买家找到矿工）
yield    = 水（钱）
买家     = 水源
```

**装再多水管，没有水源也流不出水。** 所以顺序是：

```text
① 先找到 1 个买家（BLK-2）      ← 现在没有
② 再决定 A2A 水管的形态         ← 取决于①的需求
③ 水管建成，yield 才可能从"通胀"变"需求"
```

## 8. 密钥管理 —— 你的第 8 问

**问题：** *"可以节点发密钥？在去中心网络中，有什么方法做？"*

**答案：节点不能发主密钥，但可以持有"会话密钥"。**

### 8.1 为什么节点不能发主密钥

节点发密钥 = **节点知道你的密钥** = 单点信任 = 不是去中心化。且节点被攻破就全丢。

### 8.2 去中心化里的四种做法

| 方法 | 做法 | 主密钥在哪 | 适合 |
|---|---|---|---|
| **自持（1.0 现状）** | 用户自己生成，环境变量注入 | 用户 | ✅ 最去中心 |
| **AA / ERC-4337** | Owner key 委托给 Session key | 用户（硬件/Passkey） | ✅ **推荐** |
| **MPC / 门限** | 密钥分片，无单方持有 | 分散 | 🔸 复杂 |
| **Passkey + AA** | 设备生物识别 + 智能账户 | 设备 | ✅ 体验最好 |

### 8.3 推荐：Session Delegation（`ARCHITECTURE.md` §3.4）

**这正是文档已经设计好的东西：**

```text
Owner / Smart Account                ← 资产权威（硬件钱包 / Passkey）
        │  EIP-712 签名（一次）
        ▼
Session Delegation                   ← 作用域 + 额度 + 有效期 + nonce
        │  派生
        ▼
Session Signing Key                  ← 热路径签名；只有"授权"权限，无提取权
        │  独立生成
        ▼
X25519 Encryption Key                ← 只加密；对资产零权威
```

**核心分离：**

- Session Key 只能**行使**被委托的权限，**不能扩大**权限
- Encryption Key 与签名密钥**无关**，泄露也无法签名或动资产
- Owner 可随时**递增 nonce 撤销**整个 delegation

**所以答案：** 节点可以代签**会话级**事件（省去用户每笔都签名），但**主密钥永远在用户手里，且委托可撤销、有额度上限**。

**这条同时解决了 MCP 的密钥问题（§9）。**

## 9. MCP / CLI 接入（分发杠杆）

### 9.1 玩法

用户在 IDE 里加一行 MCP 配置：

```json
{ "mcpServers": { "relayfirst": { "command": "npx", "args": ["relayfirst-mcp"] } } }
```

然后 agent 就能：发现任务 → 认领 → 执行 → 提交 → 查积分。

### 9.2 安全红线（不可妥协）

> **MCP server 绝不能持有主密钥。**

理由：MCP server 跑在 agent 进程里，agent 可能被 **prompt injection** 操控。若 MCP 能签名，攻击者就能让 agent 替用户签任意回执。

### 9.3 正确分工

| 动作 | 谁做 | 有密钥? |
|---|---|---|
| 发现 / 认领任务 | MCP | ❌ |
| 执行任务 | agent | ❌ |
| **签回执** | **本地 CLI**（或经 Session Delegation 的受限签名） | ✅ 密钥在受信边界内 |
| 提交 | MCP 转发已签字节 | ❌ |

**这与 §4.3「节点不可信但能干」是同一原则：能干活的不给信任。**

### 9.4 为什么这是杠杆

1. **解决分发** —— IDE 里已有 agent，**零安装**即可挖
2. **解决双边冷启动** —— 同一个 MCP 既能接活也能派活
3. **契合叙事** —— "你的 agent 订阅是矿机"变成一行配置

## 15. 诚实边界（必须随文档传播）

1. **A2A 节点不产生 yield，也不产生买家。** 它是水管，不是水源。**BLK-2 仍是上线硬前置。**
2. **本提案尚未生效。** 在合并进 `MVP.md` 之前，1.0 仍是唯一范围。
3. **§2.2 的"任务不限"不取消争议层，只是把它隔离到 `dispute` 模式。** 走 `recompute` 的任务仍是二值验证。
4. **`evaluator` / `dispute` 模式比 `recompute` 弱得多** —— 不要把它讲成同等可靠。
5. **"后期空投"必须是条件式措辞**，否则摧毁"不发币"退路（§3.3）。
6. **规模风险：** 本提案同时做 A2A 本体 + 挖矿引流 + 结算 + 加密 + MCP。**这比 1.0 大得多**，而 1.0 已经花了 S1–S8。**建议按 §14 分阶段，且 D4 并行推进** —— 否则会做出一个完整但没人用的系统。
